# 飞书 CalDAV 同步诊断说明

## 读者与目标

这份文档写给维护 UniCalendar 同步逻辑的开发者和未来排障者。读完后，应能在飞书 CalDAV 同步变慢、事件缺失或 Obsidian 卡住时，判断问题属于 CalDAV 协议兼容限制、缓存状态问题，还是需要切换到飞书 Open API 同步源。

## 结论

飞书 CalDAV 在部分账号上不会在时间范围查询中直接返回事件正文。它只返回事件资源地址和 etag。UniCalendar 若要拿到事件标题、时间和重复实例正文，必须再发起 `calendar-multiget` 请求。

在已诊断的真实账号上，这个第二段请求约 117 MB，耗时约 1 分钟以上，并且可能阻塞 Obsidian 的交互和退出。因此，飞书 CalDAV 路径不能把“每次强制下载正文”当作默认同步策略。

当前策略是：

1. 小型 CalDAV REPORT 用来获取 href/etag 指纹。
2. 如果已有匹配指纹，直接复用缓存事件。
3. 如果遇到旧缓存只有事件、没有指纹，则写入当前指纹并复用旧事件，避免进入巨型正文下载。
4. 只有没有可用缓存时，才尝试长 `calendar-multiget`。

这个策略优先保证 Obsidian 可用性。它不能保证飞书 CalDAV 旧缓存能获得新变更事件。

## 已观察到的行为

### REPORT 很快但没有正文

飞书 CalDAV 的时间范围 REPORT 返回很小，通常只包含：

- 事件 href
- etag
- 空的或不可用的 `calendar-data`

这足以判断资源是否变化，但不足以构造完整日历事件。

### `calendar-multiget` 很大

对同一个 href 进行 `calendar-multiget` 能拿到真实 ICS 正文，并能解析出目标事件。但在已诊断账号上，响应体约 117 MB，包含大量参与人和重复实例信息。

这会导致：

- 点击同步后长时间没有明显反馈。
- 超时后回退旧缓存，新事件仍不出现。
- 如果超时时间拉长，Obsidian 可能在请求未结束时表现为卡住，甚至关闭很慢。

### 直接 GET 不可靠

飞书 `.ics` href 直接 GET 会返回 403。飞书事件正文不能依赖普通 GET fallback，必须走 `calendar-multiget`。

## 缓存策略

飞书 CalDAV 使用“href/etag 指纹缓存”：

- 指纹相同：说明 CalDAV 资源列表未变化，复用缓存事件。
- 指纹不同且没有缓存：尝试下载正文并解析。
- 旧缓存没有指纹但有事件：写入当前指纹并复用旧事件，避免用户每次同步都触发巨型下载。

旧缓存 bootstrap 是刻意保留的止血行为。删除它会让旧用户每次同步都进入巨型 `calendar-multiget`，表现为同步按钮像没反应、Obsidian 退出变慢。

## 排障步骤

遇到飞书 CalDAV 同步慢或事件缺失时，按这个顺序判断：

1. 检查是否是飞书 CalDAV 源。
2. 看缓存是否已有 `resourceFingerprint`。
3. 如果没有指纹但有缓存事件，首次同步应只做 REPORT，然后写入指纹并复用旧事件。
4. 如果每次都进入长 `calendar-multiget`，优先怀疑旧缓存 bootstrap 失效或指纹没有持久化。
5. 如果同步很快但新事件缺失，这是当前 CalDAV 策略的已知限制，不应通过默认强制下载 117 MB 正文来修复。

## 推荐方向

飞书日历应新增独立的 Open API 同步源。Open API 可以按事件 JSON、分页和时间范围获取数据，避免 CalDAV 巨型 ICS 正文下载。

CalDAV 路径应继续保留，作为兼容路径和已有用户的低风险同步方式。但对于飞书账号的新事件准确性和性能，Open API 是更合适的长期方案。

## 不建议的修复

不要把飞书 CalDAV 默认改成每次强制下载事件正文。它能拿到新事件，但会把性能和可用性问题带回 Obsidian。

不要把飞书 CalDAV 当作普通 CalDAV 处理并切到 GET fallback。直接 GET 在飞书上会失败。

不要删除旧缓存 bootstrap。旧用户的数据文件可能只有事件缓存，没有指纹；没有 bootstrap 会导致重复巨型下载。
